# 等级与子智能体

不是每张思维导图都要做到最详细。先判断用哪一级，再决定派多少子智能体、花多少时间。参考案例是一次大型系统的全景梳理（700 多个节点、16 个一级分支、7 个子智能体并行调研），属于 L4，是最详细的一级。

## 四个等级对照

| | L1 速览 | L2 标准 | L3 详细 | L4 全景 |
|---|---|---|---|---|
| 目的 | 快速建立整体印象，或给别人讲清楚 | 理清一个项目或主题的结构，找出明显的问题 | 要据此做决定，或改造其中一块 | 整体优化、结构化、定蓝图 |
| 层级 | 2～3 级 | 3 级 | 4 级 | 4～5 级 |
| 节点数 | 约 30～80 | 约 80～200 | 约 200～450 | 约 500～1000 |
| 子智能体 | 不派；材料太散时最多 1 个帮着搜集 | 主干自己拿；不熟的分支派 1～3 个只读调研 | 3～5 个按模块并行只读调研 | 6～8 个，每条线或模块一个，再加横向的部分 |
| 来源标注 | 只给关键结论注来源 | 关键事实注来源 | 节点普遍带状态标签和来源 | 同 L3，并且关键状态都回源核过 |
| 末尾分支 | 可以没有 | 一个「问题与下一步」短分支 | 「问题与优化方向」分支 | 「问题与优化方向」按优先级分大类，加「关于这张图」 |
| 主会话要亲自做的 | 全部 | 主干、问题与下一步 | 主干、抽查关键事实、合并、问题分支 | 目的、原则、蓝图、进度、分工这些主干，横向分支，核正报告，问题分支，关于这张图 |
| 大致用时 | 十几二十分钟 | 二三十分钟 | 三四十分钟 | 约 40～60 分钟 |

层级指根节点以下的层数：一级分支是第 1 级，`build.py` 会把最深的一级打印成「deepest level N」。这些数字是参考，不是上限；用时只是大致估计，L1 和 L4 来自实际做法，L2、L3 是按比例估的，以你自己的实测为准。

## 怎么选级

看三样东西：

1. **目的**：下一步要拿这张图干什么。了解或讲解，选 L1、L2；要改其中一块，选 L3；要整体优化、定蓝图，选 L4。
2. **范围大小**：涉及多少条线、多少文件、多少个会话或模块。一页纸讲得完的东西，做 L4 是浪费；十几条线的系统，做 L2 会漏掉关键处。
3. **用户的原话**：说了「全部、完全、详细、全景」就是 L4；说了「大概、理一下、看个轮廓」就是 L1 或 L2。

怎么问：

- 选 L1、L2 时，或目的和范围都清楚时，自己定，不打扰用户。第一句回复里说明：「按 L2 做，理由是（写一句话）；要更细或更粗说一声。」
- 选 L3、L4 而目的不清、两级耗时差别大时，只问一个问题并给推荐，例如：「这张图是要据此改造某一块（L3，约半小时），还是整体定蓝图（L4，约一小时、会派六七个子智能体）？我推荐 L3。」
- 做到一半发现材料比预期多得多或少得多，可以升级或降级，告诉用户一句即可。低级的大纲可以往高级加：多加几个分支分片，再运行一次 build.py。

## 子智能体怎么用

通用规则（所有等级）：

- **一次不超过 10 个。** L4 用 6～8 个，留出余量给追加的核对任务。
- **调研用便宜的模型，派单必须写明模型。** 任务明确的搜集、整理、抽取，默认用能听懂派单的最便宜的模型（Claude Code 里用 Agent 工具并写 `model: haiku`；Codex 等其他 agent 用各自的子智能体机制）。它们可能读到过时文档，所以派单里要求附来源，关键数字和状态由主会话回原文核对。
- **需要判断的事不派便宜的模型。** 合并多份报告、核正状态、定「问题与优化方向」、验收，都是主会话自己做；确实要找人评审时用中档模型，不用最便宜的。
- **主干和目的必须主会话自己懂，不能外包。**
- 并行派出后，主会话同时写主干大纲，不干等。
- 派单格式见 [派单模板](brief-template.zh-CN.md)；报告统一落在工作目录里，文件名 `A-分支名.md`、`B-分支名.md`。
- 子智能体自报成功不算证据。收到报告后要抽查（见下）。

### 怎么切分支

- **按线或按模块切，每个子智能体一块互不重叠的材料。** 大型系统里，可以一条产品线或一个子系统一个子智能体，比如七条线切成七块。
- **横向的部分单独切**：像管线、网页层、规矩和知识层这样跨多条线的，各给一个子智能体，不要塞进某条线里。
- **切得大小差不多。** 一块材料太大（一个子智能体读不完、写不完）就拆成两块；太小就并给相邻的块。
- **整个系统共有的东西，主会话自己写。** 目的、原则、蓝图、进度、分工，以及「时间表」「数据放在哪」「当前状态」这类要把各块拼起来才看得清的横向分支。让子智能体各写各的，会得到互相对不上的版本。
- 每块要有一份明确的材料清单和建议一级分支，不要让子智能体自己去找该看什么。

### 各级具体做法

#### L1 速览

- 主会话自己读、自己写。材料散在很多地方时，最多派 1 个子智能体先把相关文件和一句话说明搜集出来。
- 只在关键结论后注来源，不要求每个节点都有。
- 一般 5～8 个一级分支，每个分支下 2～5 个节点。

#### L2 标准

- 主会话读核心文档，自己写主干。不熟的 1～3 个分支派子智能体只读调研，其余自己补。
- 末尾写一个短的「问题与下一步」分支，每条问题尽量带一句依据。
- 关键事实回源核一遍，不必逐个核。

#### L3 详细

- 主干（目的、原则、整体结构）主会话读原文自己写。
- 按模块切 3～5 个子智能体并行只读调研，统一用派单模板，报告落在工作目录里。
- 主会话抽查关键事实，特别是「已修 / 未修」「已验证 / 未验证」「在用 / 已停」这类状态。
- 节点普遍带状态标签和来源。有「问题与优化方向」分支，判断类的标【建议】。

#### L4 全景

- 6～8 个子智能体，每条线一个，再加横向的部分。
- 主会话亲自掌握目的、原则、蓝图、进度、分工这些主干，补「时间表」「数据放在哪」「当前状态」这类横向分支。
- **用最新进展核正子智能体的报告。** 参考案例里就纠正了三处：已经修好的被说成没修、已经验证的被说成没验证、正常的被说成冲突。原因都是子智能体读到了过时的文档。
- 「问题与优化方向」按优先级分大类（参考案例是先保数据、再收文档、再理代码、再推蓝图），标【建议】的是整理方的判断、还没定。
- 最后有「关于这张图」：怎么来的、更正了什么、怎么更新、怎么给反馈。

## 收到报告后怎么抽查

主会话要回源文件，不要只看报告。每份报告至少抽查：

1. **状态类**：已修 / 未修、已验证 / 未验证、在用 / 已停。拿最新的进展记录、日志或提交记录对。
2. **时刻、数量、路径**：报告里随手挑 3～5 个，实际打开文件看。
3. **报告自己标的「拿不准」**：逐条回源解决，不要原样放进图里。
4. **互相矛盾的地方**：两份报告对同一件事说法不同时，以源文件和最新进展为准，在对应节点写明采用哪个。

核过并改正的地方，写进「关于这张图」的「更正了什么」，让读者知道哪些是纠正过的。
