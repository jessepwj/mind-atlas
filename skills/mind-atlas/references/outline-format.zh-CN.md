# 大纲写法

`scripts/build.py` 读一份缩进的 Markdown 嵌套列表，生成页面。能用的写法就这些，别加别的。可以直接照仓库 `examples/` 目录里的完整示例抄。

## 工作目录里有什么

| 文件 | 谁写 | 作用 |
|---|---|---|
| `meta.json` | 整理方 | 页面标题、语言、等级、说明、要拼哪些分片 |
| `outline-*.md` | 整理方 | 大纲分片，按 `parts` 的顺序拼成一份 |
| `outline.md` | build.py 自动写 | 拼好的整份大纲，只用来检查，别手改（下次会被覆盖） |
| `A-xxx.md` 等 | 子智能体 | 调研报告，原料，不会被拼进页面 |
| `replies.json` | reply.py 写 | 对用户反馈的回复，没有也行 |
| `<title>.html`（或 `out`） | build.py 生成 | 成品，单文件，双击能开 |

工作目录放在项目里的 `mindmaps/<主题>/`，或用户指定的地方。

## 大纲格式

```
# 根节点标题 ｜ 根节点说明
- 一级分支 【在用】 ｜ 说明 〔来源〕
  - 二级节点
    - 三级节点 【问题】 ｜ 说明
      续行：缩进更深、不以「- 」开头的行，并进上一个节点的说明。
```

- **每级缩进两个空格**，只能用空格，不能用 Tab。子节点比父节点正好多缩进 2 格，跳级会报错。
- 整份大纲**只有一个 `# 根节点`**，写在最前面。在后面的分片里再写一行 `# 标题` 会报错。其他以 `#` 开头的行（比如从报告里复制来的 `## 小标题`）不是节点，会被并进上一个节点的说明并给出警告，请改写成以短横线开头的列表节点。
- 根节点的子节点（一级分支）缩进为 0，写成 `- 标题`。
- 标题和说明之间用 ` ｜ `（全角竖线，前后各一个空格）隔开，英文写法是 ` | `。第一个分隔符前是标题，后面全是说明。两边没有空格的竖线（比如 `a|b`）不算分隔符。标题里一定要出现 ` | ` 时，去掉两边的空格，或换个符号。
- `〔来源〕`（英文写法 `[src: ...]`）可以写在节点任何位置，一般放在末尾；一个节点可以有多个，页面上合并显示。
- 状态标签 `【在用】`（英文写法 `[active]`）可以写多个，一般紧跟标题，放在分隔符前面。
- 空行和 `<!-- 注释 -->` 整行会被忽略，注释可以跨多行。
- 分片就是文本直接拼接，**只看缩进**。所以可以在主干文件里写一个分支的头节点，把它的子节点放在另一个分片里、整体多缩进两格接在后面（英文示例里的 `outline-A-inventory.md` 就是这样接在主干最后一个节点下面的）。
- 以 `*` 或 `+` 开头的行不是节点（只有 `-` 才开始一个节点），会被当成说明文字，`build.py` 会给出警告。
- 续行整行都属于上一个节点的说明，里面可以带标签和来源，但不会再被拆成标题和说明。

### 中英文写法都认

不管 `lang` 设成什么，两种写法永远都认，可以混着用。

| 要素 | 英文（ASCII）写法 | 中文写法 |
|---|---|---|
| 标题和说明的分隔 | ` \| `（竖线，前后各一个空格） | ` ｜ `（全角竖线，前后各一个空格） |
| 来源 | `[src: ...]` 或 `[source: ...]` | `〔...〕` |
| 状态标签 | `[active]` | `【在用】` |

标签词写在这一行的任何位置都算标签，连说明里也一样，所以一句讲标签的话里，那个词会被吞掉。想让方括号里的英文词原样显示，前面加反斜杠：`\[todo]` 显示成文字 `[todo]`，不当作标签。中文的 `【】` 标签不能转义，换成别的引号来写，比如 “建议”。只有标签词本身和 `[src:`、`[source:` 是特殊的，别的方括号（比如 `a[0]`、`[maybe]`）都是普通文字。

## meta.json 字段

| 字段 | 必填 | 含义 |
|---|---|---|
| `title` | 是 | 页面标题，没写 `out` 时也是生成的 html 文件名 |
| `lang` | 强烈建议写 | `"zh"` 或 `"en"`，页面界面的语言。**默认 `"zh"`**，英文图一定要写 `"en"` |
| `id` | 建议写 | 页面的稳定标识，用户的反馈存在浏览器里就按它分开。不写就用 title，之后改 title 会让原来写的反馈在这个页面里找不到。写一个英文短名，不要和你的其他图重名（浏览器在本地文件之间共用存储，id 相同反馈会串），以后不改 |
| `level` | 建议写 | 梳理等级，比如 `L4 全景`，显示在页头 |
| `desc` | 建议写 | 页头一句说明：怎么做出来的、核对到什么程度 |
| `search_hint` | 否 | 搜索框里的提示，举几个这张图里真有的词 |
| `parts` | 否 | 按顺序拼的分片文件名列表。不写就读同目录的 `outline.md` |
| `out` | 否 | 输出文件名（只能是文件名，不能带路径），不写就是 `<title>.html` |

不认识的字段会被忽略并给出警告，写错字段名不会悄悄失效。

## 状态标签（十种，只能用这些）

| 英文写法 | 中文写法 | 什么时候用 |
|---|---|---|
| `[active]` | 【在用】 | 现在正在运转的东西、功能、定时任务、规矩 |
| `[stopped]` | 【已停】 | 以前用过，现在停了、退役了、被替换了 |
| `[in progress]` | 【进行中】 | 正在做，还没做完 |
| `[todo]` | 【待做】 | 已经决定要做、或明显该做，还没动手 |
| `[issue]` | 【问题】 | 已经确认的毛病、缺口、互相矛盾的地方 |
| `[done]` | 【已完成】 | 做成了的事，常用在发展历程和蓝图的步骤上 |
| `[decided]` | 【已定】 | 用户或负责人拍板的决定、原则、边界，不再讨论 |
| `[waiting]` | 【等别人】 | 卡在别人那里：用户、别的会话、第三方 |
| `[risk]` | 【风险】 | 还没出事，但可能出事的地方 |
| `[proposal]` | 【建议】 | 整理方的判断，还没定，要用户看过再做 |

英文标签词不分大小写（`[Active]` 也行）。

**【建议】的用法要守住：** 凡是整理方自己提出的做法、排序、取舍，都标【建议】，让读者一眼分清「事实」和「我的判断」。用户点头之后再改成【已定】或【待做】。

不同等级用多少：L1 基本不用；L2 在问题和关键事实上用；L3、L4 普遍用（参考案例那张 700 多个节点的图里，带标签的约两成）。**不是每个节点都要标，没有状态可说就不标。**

## 节点怎么写

1. **标题写成短的完整句或名词短语**，在图上一行读得懂。细节放到分隔符后面的说明里，不要把一整段塞进标题。
2. **不许用省略号截半句**（中文省略号和三个英文点都不行）。写不下就换成短的完整句，或拆成子节点。`build.py` 会检查，发现就报警告。
3. **不只报条数，要说是什么。** 反例：「共 12 个脚本」。正例：「12 个脚本，分采集、转写、发布三类，采集 5 个」。
4. **一个节点一个意思。** 说明里出现「第一」「第二」这样分条列举，就该拆成子节点。
5. **同一个父节点下，标题不要重名。** 反馈的引用位置是靠「父标题 › 子标题」路径找的；重名找不准，改名后旧的引用也会找不到（页面会提示「图里找不到这一条了，可能改过名」）。`build.py` 发现重名会警告。
6. **日期写具体**：写 `10-16`，不写「昨天」「最近」。图会被人在很久以后打开。
7. **一个父节点下子节点一般不超过 9 个**，多了加一层分组。
8. **来源写在节点后面**：文件路径、页面名、会话名、日期。关键事实必须有，其他可以没有。
9. **私人内容、口令、密钥不进图**，只写在哪个文件、什么权限。
10. **说明里写事实，判断另起节点标【建议】**，不要混在同一句里。

## 几种固定分支的写法

- **目的与蓝图**（L2 以上）：最终要什么、分几步、各步的状态、明确不做的、一直有效的边界。每条尽量带用户的原话和日期，标【已定】。
- **发展历程**：按日期排，一天一个节点，当天做成的事放子节点，标【已完成】。
- **时间表**：把分散在各处的定时、日期按时间顺序拼在一起，是横向分支，主会话自己写。
- **数据放在哪**：目录结构和每类数据的一句话说明，只写位置，不抄内容。
- **问题与优化方向**：先按优先级分大类（一、二、三），每类下面是问题，问题下面是【建议】。大类标题写目的，比如「先保数据」「收文档」「理代码」。
- **关于这张图**（L4）：怎么来的、更正了什么、右栏反馈怎么用、怎么更新。

## 把子智能体报告改写成大纲

报告是 Markdown 嵌套列表，缩进已经接近大纲，但要改：

1. 括号里的来源改成 `〔来源〕`（或 `[src: 来源]`），放到节点末尾。
2. 状态标签只留前面表里的十种，其余改写。
3. 过长的标题拆成「标题 ｜ 说明」。
4. 用最新进展和源文件核正状态（已修 / 未修、已验证 / 未验证），把过时的改掉。
5. 重复的合并，互相矛盾的按源文件采用一个，写明依据。
6. 整份缩进调整到它在图里的位置（接在主干的分支头节点下面时，多缩进两格）。
7. 改好另存为 `outline-<编号>.md`，在 `meta.json` 的 `parts` 里排好顺序。

## 生成和检查

```
python3 <skill_dir>/scripts/build.py <工作目录>
```

它会打印节点总数、最深层级、文件大小、回复条数，再逐行列出每个一级分支的节点数（某支数字明显偏小或偏大，往往是节点挂错了父节点），并检查：

- 结构错误直接停下来并指出文件和行号：用了 Tab 缩进、缩进不是 2 的整数倍、缩进跳级、第二个 `# 根节点`、根节点之前就有内容、大纲为空、不支持的 `lang`。
- 警告（打印到 stderr，页面照常生成）：省略号截断、空标题、同级标题重名、缺的分片（`missing part: 文件名`，页面会少了那一块，要补上）、不认识的 `meta.json` 字段、以 `*` 或 `+` 开头的行、以 `#` 开头的行、缩进不比所属节点更深的续行、`meta.json` 没写 `lang`。

对照等级的目标（节点数和层级见 [等级与子智能体](levels.zh-CN.md)）看数字是否合理：L2 只有 30 个节点，或 L4 只有 200 个，说明漏了东西。缩进写错不一定报错，只会把节点挂到错的父节点下面，所以生成后要在页面上翻一遍一级分支，看每支下面的内容对不对。

`build.py <工作目录> --no-paths` 生成的页面里不带页面文件的绝对路径和回复命令。页面要发给别人、放到网站上时用它。
